# ShortlistAI

Give it a job requirement ("10 housekeeping staff, Bangalore, 1+ year experience, Kannada or
Hindi") and a pile of resumes. It returns a ranked shortlist with a reason for each candidate
that cites what the resume actually says, and a recruiter approves or edits it before it is final.

Built with LangGraph and Gemini. Plan and progress: [docs/PLAN.md](docs/PLAN.md).

> **All resumes in this repo are synthetic.** They are generated by `shortlist.synthetic`;
> every person, employer and school name is invented, phone numbers are masked and emails use
> `example.com`.

## How it works

```
START -> parse -+-> parse again      (a resume failed; one retry)
                +-> manual review    (failed twice: a person reads it) -> match
                +-> match -> rank -> recruiter review (pause) -> END
```

| Step | Plain code | LLM (Gemini) |
|---|---|---|
| **parse** (`shortlist.parse`) | adds up months per job ("Present" = 2026-10-01), maps city spellings | resume text -> fields, with skills, certificates and languages restricted to the catalog's names by the JSON schema |
| **match** (`shortlist.match`) | experience, location, languages, certificates, salary, notice: pass / near miss / fail / unknown, each naming the fields it read | one call per job: is each previous title the same, related or different work? |
| **rank** (`shortlist.rank`) | tier (shortlist / call / reject) and score from the checks | one call per job: a short reason per candidate, citing fields; a checker rejects reasons that cite nothing, cite a wrong value, state an unbacked number or guess gender, then retries once, then falls back to a plain reason |
| **review** (`shortlist.graph`) | `interrupt` until the recruiter approves, edits or rejects; every decision goes to `runs/feedback.jsonl` | - |

State is saved after every step in SQLite (`runs/checkpoints.sqlite`), so a session waiting
for review survives a restart. The near-miss slack (how far over budget or notice is still
worth a call) is set per job, like a recruiter would, in `catalog.JOBS`.

## Data

`make data` writes (deterministic, seed 42):

| Path | What it is |
|---|---|
| `data/jobs.json` | 5 job postings: housekeeping (Bengaluru), receptionist (Pune), security guard (Hyderabad), delivery rider (Chennai), customer support (Noida) |
| `data/resumes/R001.txt ...` | 150 resumes, 30 per job |
| `data/ground_truth.jsonl` | per resume: the fields the text states, the generator's fit label and why |
| `data/summary.json` | counts by job, label, format and missing field |
| `data/labels/labels.csv` | 50 resumes (10 per job) for hand labelling |

**How a resume is made.** Each resume is generated for one job and aimed at a tier by starting
from a candidate who meets every requirement and applying "misses":

- *good*: no misses
- *borderline*: one soft miss - a related role (Office Boy for housekeeping), a few months short
  on experience, lives in a nearby city, salary up to 25% over budget, notice up to 2x the
  limit, required licence not listed, languages or location not stated
- *poor*: one hard miss - a different role, a far city, no experience when some is required,
  doesn't speak the required language, salary or notice far over the limit - or two soft misses

The candidate is then written in one of five formats (formal CV, bullet list, cover-letter
prose, Hinglish WhatsApp-style message, application form with a table), with random omissions,
typos in about a third of resumes, and some formal CVs and forms turned into upper-case,
run-together text like a bad PDF extract. Skills, cities, languages, certificates, salaries
("15k", "Rs. 15,000/-", "2.16 LPA"), notice periods ("Immediate joiner", "2 weeks") and dates
("Jan 2021", "01/2021", "Jan-21", "Till date") each appear in several forms.

**Ground truth** records only what the text states: if a resume leaves out the salary, the
truth is `null`, not the hidden value. Experience counts "Present" up to 2026-10-01.

**Labels.** The generator re-derives each fit label from the visible fields with a fixed rule
(`rubric_fit`). Those are the generator's rules, not a recruiter's judgment, so 50 resumes are
also labelled by hand (`make label`, which hides the generator's label). Agreement between the
two is reported once the hand labels exist.

## Setup

```
make venv && make install
make test
```

Windows needs GNU make: `winget install ezwinports.make`. Copy `.env.example` to `.env` and
paste a free Gemini key from https://aistudio.google.com/apikey after `GOOGLE_API_KEY=`.
`results/` holds the caches from the evaluation runs, so the demos on the synthetic resumes
work without spending API quota.

| Command | What it does |
|---|---|
| `make data` | regenerate the synthetic data (keeps `data/labels/labels.csv`) |
| `make label` | hand-label the 50 sampled resumes, blind to the generator's label |
| `make demo` | rank job J1 in the terminal and review it; `python -m shortlist.cli review <id>` resumes a paused session |
| `make api` | HTTP API, docs at http://127.0.0.1:8000/docs |
| `make ui` | Streamlit UI for the recruiter (start `make api` first) |
| `make eval` | all evaluations, then `make report` rewrites the Results below |
| `docker compose up --build` | API on :8000 and UI on :8501 (written, but not yet built: Docker was not available on the development machine) |

Tracing: set `LANGSMITH_TRACING=true` and `LANGSMITH_API_KEY` in `.env` to see every graph
run, with each Gemini call inside it, in LangSmith.

### Parsing

`gemini-3.1-flash-lite`, 150 resumes, 0 parse failures, median 1.85 s per resume (`results/parse_accuracy_gemini-3.1-flash-lite.json`). A field is correct only if it equals the ground truth after case, spacing and punctuation are normalised; list fields must match as whole sets; a value filled in where the resume says nothing is an error.

| Field | Accuracy |
|---|---|
| name | 1.000 |
| job_titles | 0.993 |
| skills | 0.620 |
| years_experience | 0.993 |
| location | 1.000 |
| languages | 0.953 |
| certifications | 0.973 |
| education | 0.980 |
| institution | 0.993 |
| expected_salary_monthly_inr | 1.000 |
| notice_period_days | 0.993 |
| **mean over fields** | **0.955** |
| all 11 fields correct | 0.553 |

Skills are the weak field: per item, precision 0.975 and recall 0.908 (F1 0.940), but one missed skill makes the set wrong. Most misses are synonyms not mapped to the canonical name ("attending calls" -> "phone handling"). The prompt lists only canonical names, not the catalog's spellings, so this measures the LLM, not a lookup table. Caveat: the prompt was adjusted once after reading 5 of these resumes, so this is not a held-out set.

### Matching

From `results/match_gemini-3.1-flash-lite.json`. Plain code checks experience, location, languages, certificates, salary and notice; each check is pass, soft (a near miss worth a call), fail or unknown. How far past a limit is still a near miss is the recruiter's slack, set per job (`salary_stretch_pct`, `notice_stretch_days`, `years_stretch`), chosen without looking at the generator's labelling rule.

**Parse errors barely reach matching:** run on parsed fields instead of ground truth, each check gives the same result for 98.7% to 100.0% of the 150 resumes.

**The one LLM call, is a previous title the same kind of work?** On 39 (job, title) pairs the LLM agrees with the generator's role catalog on 0.769. The catalog is one opinion; most disagreements are judgment calls (Receptionist for a Security Guard job: catalog *different*, LLM *related*). One is a plain LLM mistake: "Bike Rider" called *related*, not *same*, for a Delivery Executive job.

| Catalog says | LLM: same | LLM: related | LLM: different |
|---|---|---|---|
| same | 18 | 1 | 0 |
| related | 0 | 4 | 3 |
| different | 0 | 5 | 8 |

### Ranking and ablation

From `results/rank_gemini-3.1-flash-lite.json`. Each job's candidates ranked three ways: **keyword** (BM25 of the job text over the resume text), **embedding** (`gemini-embedding-001` similarity) and the full **agent** (parse, match, rank). Averaged over the 5 jobs; NDCG gains good = 2, borderline = 1, poor = 0.

| System | P@5, hand labels | NDCG@10, hand labels | P@5, generator labels | NDCG@10, generator labels |
|---|---|---|---|---|
| keyword | TBD | TBD | 0.280 | 0.506 |
| embedding | TBD | TBD | 0.440 | 0.598 |
| agent | TBD | TBD | 1.000 | 0.995 |

Hand labels: 0 of 50 labelled so far (agreement of the generator's labels with them: TBD); the hand-label columns stay TBD until `make label` is done. **Read the generator-label columns with care:** those labels come from rules that share the near-miss idea with the matcher, so the agent has a built-in advantage there. They show the pipeline does what it was built to do, not that it agrees with a recruiter.

The agent's tier (shortlist / call / reject) matches the generator's label for 0.820 of the 150 candidates (hand labels: TBD). They disagree both ways: the per-job slack is tighter than the generator's (10% over budget instead of 25%), so the agent rejects some of its borderline candidates, and where the generator rejects anyone with two near misses or gaps, the agent asks for a call.

**Reasons.** Of 150 reasons, 84.0% passed the grounding check first time, 15.3% after one retry and 0.7% fell back to a plain reason built from the checks. The check rejects a reason that cites nothing, cites a value the resume does not hold, states a number found in neither its citations nor the checks, or guesses gender. It checks citations and numbers, not every word of the sentence.

### Fairness

From `results/fairness_gemini-3.1-flash-lite.json`. Resumes re-run through the whole pipeline with only the name (to one from another language group, which often also changes the implied gender and religion) or only the institution (another invented one, same level and town) changed. "Same text again" re-parses the unchanged resume and measures the LLM's own noise.

| Variant | Resumes | Mean abs score change | Max | Tier changed | Rank moved | Embedding baseline: rank moved |
|---|---|---|---|---|---|---|
| same text again | 30 | 0 | 0 | 0 | 0 | - |
| name swapped | 30 | 0.17 | 5 | 0 | 1 | 21 |
| college swapped | 30 | 0.17 | 5 | 0 | 1 | 9 |

The agent's score never reads the name or the institution, so it can only move when the LLM parses other fields differently. Re-parsing the same text changed fields in 0 of 30 resumes, but a swap changed other fields (mostly skills) in 7 (name) and 9 (college): the parser is sensitive to text it should ignore. The effect on the decision was small here (see the table), but it is not zero. The embedding baseline reads the raw text, names included, and moves more often. One swap per resume on a small sample: a smoke test, not a bias audit.

## Limitations

- Synthetic data only. Real resumes are messier (scans, tables, several languages in one
  document), and the five formats here were written by the same generator that labels them.
- The hand labels are the real test of ranking quality, and they are not done yet.
- The generator's labels and the matcher share the idea of a near miss, so agreement with them
  is not independent evidence.
- The reason checker checks citations and numbers, not every word of a sentence.
- Free-tier Gemini: rate limits and daily quotas shape what could be run (one model end to
  end; small fairness sample).
